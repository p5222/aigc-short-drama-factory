# 后台创作质量与评测系统重构规范

版本：2026-07-10
适用范围：漫剧前台四阶段工作台、后台创作质量中心、模型与提示词优化流程

## 1. 结论

当前系统的核心目标不是控制创作者发布，而是根据创作者在每个阶段生成的真实内容，判断内容、资产、分镜、成片中哪个模块最需要优化，并验证更换模型或提示词后是否真正改善。

目标信息架构收敛为 6 个工作区：

1. 总览
2. 事件与 VOC
3. 数据集
4. 实验评测
5. 模型与成本
6. 优化回流

统一闭环：

`前台质量信号 -> 问题归因 -> 样本沉淀 -> 基线评测 -> 模型/Prompt 对比 -> 优化复测 -> 结果回流`

## 2. 对标产品取舍

| 产品 | 可借鉴能力 | 本项目适配方式 | 不直接照搬 |
| --- | --- | --- | --- |
| LangSmith | 数据集、实验、结果对比、人工标注队列 | 用户反馈进入处置队列，代表性 badcase 转为版本化数据集 | 不把漫剧作品拆成纯文本 input/output |
| Langfuse | Trace、Score、Dataset、Experiment 串联 | 项目、任务、资产、模型、Prompt 版本、评分保持可追溯 | 不把 trace 列表作为后台主导航 |
| Braintrust | 基线/候选实验和 scorer 组合 | 同一数据集对比基线模型、候选模型和评分器 | 不先建设通用 SDK 平台 |
| Promptfoo | 断言矩阵、回归、红队、CI 门禁 | 为四阶段建立硬性断言与回归阈值，门禁输出明确阻塞原因 | 不以 YAML 配置取代运营后台 |

## 3. 现状逻辑审计

### 3.1 已有且可复用

- `UserFeedback` 已有状态、优先级、根因、负责人、处理结论、样本集关联字段，可直接作为用户反馈工单。
- `EvaluationDataset` 可保存项目集合、阶段、来源和筛选条件。
- `EvaluationRun.datasetSnapshot` 已保存运行时不可变快照，能保证历史结果可复现。
- `QualityReport` 已记录评分器类型、维度分、问题、建议、Prompt 版本、模型与供应商。
- 模型监控已有成功率、失败率、P95、积分、成本和错误聚合。
- 资产溯源已有用户、项目、缩略图、模型路由、评分、反馈和积分消耗。

### 3.2 主要问题与风险

| 级别 | 问题 | 影响 | 处理方向 |
| --- | --- | --- | --- |
| P0 | 评测结果没有稳定关联模型、提示词版本和对比实验 | 无法证明一次优化是否有效 | 评测运行保存配置快照，实验绑定基线与候选运行 |
| P0 | 任务失败、模型错误、评测失败只是派生信号 | 无法形成阶段瓶颈结论 | 使用数据库聚合形成四阶段优化诊断，不强制转工单 |
| P1 | 9 个平级入口拆散同一闭环 | 导航重复、上下文丢失、处理步骤过长 | 收敛为 6 个业务工作区 |
| P1 | 前台四阶段、后台五阶段名称不一致 | 用户和运营对同一问题使用不同口径 | 展示层聚合，底层保留细粒度评分 |
| P1 | `PromptVersion`、`ExperimentRun` 数据模型未接 API/UI | 无法形成候选 Prompt 与实验记录闭环 | 统一 Prompt 版本来源，再接实验 API |
| P1 | 质量中心在内存聚合大量任务、报告和反馈 | 数据增长后响应时间和口径会漂移 | 数据库聚合、分页、时间窗和异步快照 |
| P2 | 总览指标缺少时间范围和环比基线 | 数字无法支持异常判断 | 默认 7 天，对比前 7 天并展示样本量 |
| P2 | 数据集只有项目粒度 | 一个项目中的单一坏镜头会带入大量无关数据 | 后续支持任务、资产、镜头级样本项 |

## 4. 前后台四阶段质量契约

前台继续保持四步创作，后台数据库保留五个评分阶段。映射如下：

| 前台阶段 | 后台评分阶段 | 核心产物 | 核心质量维度 | 优化诊断重点 |
| --- | --- | --- | --- | --- |
| 内容 | `script` | 故事结构、分集、对白 | 完整性、逻辑、角色动机、对白可拍性、合规 | 结构缺失、严重内容风险不得进入资产阶段 |
| 资产 | `character` + `image` | 角色设定、参考图、场景资产 | 身份一致、风格一致、引用完整、可复用性 | 主角未锁定、参考图不可用不得进入分镜 |
| 分镜 | `storyboard` | 镜头表、画面提示、节奏 | 镜头覆盖、时空连续、角色连续、生成可执行性 | 关键情节漏镜、角色引用断链不得批量生成 |
| 成片 | `video` | 视频片段、配音、导出 | 生成成功、视觉连续、音画同步、时长、成本 | 定位不可用片段、失败模型、耗时和成本异常 |

聚合只发生在查询和展示层，不修改历史 `QualityReport.stage`，避免数据迁移和评分口径丢失。

## 5. 评测对象与单一事实来源

| 对象 | 职责 | 单一事实来源 |
| --- | --- | --- |
| 用户反馈工单 | 用户声音、回访、补偿、归因、处理结果 | `UserFeedback` |
| 系统质量信号 | 任务失败、模型异常、评测失败 | 数据库聚合后的阶段诊断与只读明细 |
| 数据集 | 可复用的标杆、问题、回归和边界案例 | `EvaluationDataset` + 后续 `EvaluationSampleItem` |
| 评测运行 | 对固定样本和配置执行评分 | `EvaluationRun` + `datasetSnapshot` |
| 评测报告 | 单项目、单阶段、单评分器结果 | `QualityReport` |
| Prompt 版本 | 候选内容、状态、版本和改动说明 | `PromptVersion` |
| 实验 | 基线与候选对比、假设、指标、结果 | `ExperimentRun`，需连接评测运行 ID |

## 6. 完整评测方法

### 6.1 四层评分

1. 规则评分：结构完整、字段存在、引用有效、生成任务状态、资产覆盖率。
2. AI 评分：故事逻辑、角色一致性、镜头连续性、视觉可用性等主观维度。
3. 人工评分：你对标杆案例、复杂 badcase 和实验结论进行复核。
4. 线上评分：用户可用性、重新生成率、阶段放弃率、生成成功率、P95、积分与成本。

任何阶段不得只用一个总分。总分用于排序，优化结论还必须读取具体维度、失败样本、用户反馈、耗时和成本。

### 6.2 数据集分层

| 类型 | 用途 | 建议最低覆盖 |
| --- | --- | --- |
| Golden | 验证标准能力上限 | 每阶段 20 个稳定案例 |
| Badcase | 验证已知线上问题 | 每个高频根因至少 5 个案例 |
| Regression | 防止历史问题复发 | 所有 P0/P1 修复必须进入 |
| Boundary | 极端输入、长文本、复杂角色、多镜头 | 每阶段至少 10 个边界案例 |
| Safety | 内容与生成安全 | 作为风险诊断样本长期保留 |

### 6.3 实验比较

每次候选变更必须记录：

- 假设：为什么变更。
- 基线：线上 Prompt/模型/流程版本。
- 候选：待验证版本。
- 数据集快照：运行时项目、资产和阶段集合。
- 评分器版本：规则版本、AI 评分 Prompt 与模型。
- 结果：分阶段分数、通过率、失败样本、成本和耗时差异。
- 结论：候选更好、基线更好或表现持平，以及下一轮优化动作。

### 6.4 默认优化验证线

| 验证项 | 候选有效 | 需要继续优化 |
| --- | --- | --- |
| 核心回归 | Regression 通过率 100% | 任一历史 P0/P1 复发 |
| 综合质量 | 候选均分不低于基线，关键阶段不下降超过 2 分 | 内容或资产阶段显著下降 |
| 用户反馈 | 同类不可用反馈下降 | 高频投诉仍未归因或继续增长 |
| 模型健康 | 核心模型成功率 >= 98%，P95 不劣化超过 20% | 核心模型阻塞或错误突增 |
| 成本 | 单有效成片成本不高于预算，或质量收益有审批说明 | 成本上涨且无质量收益 |
| 溯源 | Prompt、模型、任务、资产和报告可追溯率 100% | 任一核心链路无法定位版本 |

阈值必须按时间窗和样本量展示。样本不足时状态为“待验证”，不能自动显示“通过”。

## 7. 重构本身的验收评测体系

| 维度 | 指标 | 验收线 |
| --- | --- | --- |
| 信息架构 | 一级质量入口数 | 6 个，且没有同义重复入口 |
| 操作效率 | 从 P1 反馈到“已归因” | 不超过 3 次主要点击 |
| 闭环能力 | 反馈转数据集 | 根因、结论、关联项目完整后一次完成 |
| 数据正确性 | 页面状态刷新 | 保存后工单、总览和样本数口径一致 |
| 决策可解释 | 实验结果 | 显示基线、候选、分数差、通过率差和分阶段差值 |
| 前后台一致 | 阶段名称 | 所有主视图使用内容/资产/分镜/成片 |
| 可追溯性 | 评测运行 | 能定位数据集快照、模型、Prompt 版本和报告 |
| 性能 | 质量中心 API P95 | 7 天常用窗口 <= 800ms；大列表分页 |
| 可用性 | 桌面与移动端 | 无横向溢出、无文本遮挡、键盘可操作 |

## 8. 迭代顺序

### 已完成的第一步

- 9 个入口收敛为 6 个工作区。
- 将此前未接入的反馈处置台接入“事件与 VOC”。
- 用户反馈可归因、指派、记录结论、关闭并沉淀为评测数据集。
- 系统派生事件与可编辑工单在 UI 上分开。
- 建立前台四阶段与后台五评分项的契约矩阵。
- 模型监控统一为四阶段筛选，并展示真实成本。
- 旧的“用户反馈/评测闭环”链接兼容到新工作区。

### 当前新增能力

- `PromptVersion` 已接通版本创建、启用、归档和指定版本评测。
- `ExperimentRun` 已关联基线/候选 `EvaluationRun`，自动计算平均分、通过率和阶段差值。
- 四阶段瓶颈由数据库聚合生成，质量列表使用分页读取。
- 单人处理流程取消负责人必填，只记录根因、优化动作和复测结论。

### 下一阶段：提高样本精度

- 为数据集增加镜头、任务、资产级 `EvaluationSampleItem`，避免整个项目作为最小样本。
- 增加逐样本 diff，直接显示候选改善和退化的具体项目或镜头。
- 统计评分器一致性，避免评分提示词变化造成虚假的质量提升。

### 后续自动化

- 候选模型或 Prompt 变更时自动运行固定核心回归集。
- 连续记录每轮优化前后差值，形成模型、Prompt 和阶段问题的趋势图。

## 9. 明确不做的事情

- 不把任务失败快照直接伪装成可编辑工单。
- 不为了四阶段 UI 删除角色或图片的细粒度历史评分。
- 不用一个全局平均分代替具体阶段、具体样本和具体版本的对比结论。
- 不在没有样本量、时间范围和基线时给出确定性质量结论。
- 不同时维护两套 Prompt 版本事实来源。
