# 商用可靠性迭代

本轮接续前后台 UI 重构，处理发布容量、运行期限流、支付开放边界和备份恢复。UI 通过验收不等同于供应商生成质量或现金支付通过验收。

## 本轮实现

- IP 限流记录有容量上限和定时过期回收，超限返回 `Retry-After`。限流提前到 JSON 解析和私有媒体权限查询之前，登录写请求和普通读取分开计数。当前仍是单 API 进程限流；多副本扩容前应使用共享限流存储。
- 生产环境始终禁用模拟支付，即使误设置 `ENABLE_MOCK_PAYMENT=true` 也无法模拟充值。未接入真实网关时，在线下单返回明确提示；卡密购买和兑换继续使用原有流程。
- 生产镜像分离构建阶段，仅携带 API 的生产依赖、数据库工具、编译结果和前端静态资源。Prisma 和共享包明确归入运行依赖，重新生成打包后的 Prisma Client。运行和发布直接调用镜像内 Prisma CLI，避免 pnpm 运行前自动安装尝试重新解析原 workspace。
- 发布在备份前检查磁盘；构建及容器切换前再次检查。默认本机构建需要 6 GiB 可用空间，加载已验证镜像需要 1 GiB 运行余量，备份前还加上最近完整备份体积的 125%。这是预估保护，不能阻止同机其他应用同时写满磁盘。
- 源码备份排除已被同步流程排除的 `dist`、`.pnpm-store`、`node_modules` 和 Python 缓存，保留源码、服务器配置、独立数据库与媒体归档。
- 主分支 CI 输出带提交版本标签的压缩镜像和 SHA256 校验文件，保留 7 天。服务器只复用标签内提交与发布提交一致的镜像，否则仍需构建并通过容量检查。
- `verify_backup_restore.sh` 将完整备份恢复到无网络、无宿主端口、使用 tmpfs 的临时 PostgreSQL，检查完整恢复与核心表可读性，随后删除临时容器；不连接或覆盖生产数据库。媒体和源码归档校验可解包，但此脚本不替代全站灾难恢复演练。

## 低磁盘服务器发布

1. PR 全部检查通过后合并；等待合并提交的主分支 CI 完成。
2. 从该次成功 CI 下载 `manjiao-image-<完整提交>`，核对 `manjiao-image.tar.gz.sha256`，传入目标服务器后再次核对。
3. `docker load -i manjiao-image.tar.gz` 导入镜像；保留当前运行及上一可回退镜像。通过后移除本次传输的临时压缩包。
4. 本轮首次启用需使用 `deploy/install_git_hook.sh` 原子安装本提交的 `server_git_post_receive.sh`。安装钩子不发布应用。
5. 本地切换到完全相同的 GitHub main 后运行 `pnpm deploy:server`。服务端仍执行备份、容量检查、受保护的数据库同步、启动和 `/ready` 校验，只跳过重复构建。
6. 核对 `GitHub main = server main = deployed = public revision`，并验收公开页面资源。磁盘检查失败时先处理容量，不要盲目调低保护阈值。

## 恢复演练

在服务器执行 `bash /opt/manjiao/deploy/verify_backup_restore.sh /opt/manjiao-backups/<完整备份目录>`。脚本对 PostgreSQL 16 备份进行真实恢复；临时数据库容量上限 512 MiB，超过时应在独立恢复主机规划容量后验证。输出仅含表数量、业务记录总数和耗时，不输出账号内容、凭证或剧本。
