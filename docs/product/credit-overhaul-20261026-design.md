# 积分系统大迭代设计

当前阶段：产品方案与积分迭代已实现，完成整数成本计价、任务价格快照、资金批次、计量采集、后台积分中心及前台分页明细。最终验证与发布状态见 `outputs/credit-overhaul-20261026/验收记录.md`，本文件记录实际技术契约。

## 已确认需求

用户要求“积分的使用，扣费，计费，以及官方API的计费如何换算到我这，利润百分之40；以及后台的积分系统；详细的全部积分相关的去做一个方案并完成开发迭代”。用户已同时授权方案和开发，无需在方案完成后重新请求批准。例行 GitHub 同步和腾讯云发布也已有持续授权。

本轮解释：40% 为目标毛利率，即 `(售价 - 官方 API 成本) / 售价 = 40%`，基础售价为成本 `/ 0.6`；这是已向用户说明的产品假设，需在最终方案醒目标注并支持后台调整。基础名义汇率沿用充值规模，建议 1 元 = 100 积分；不是国际货币实时汇率。充值赠送、套餐兑换、会员折扣会改变实收积分价值，必须展示其对毛利的影响。赠送积分属于推广成本，不能声称其产生现金收入。

## 现状与必须修复

- `CreditAccount.balance` 含被冻结的余额；可用余额应为 `balance - frozenBalance`。当前前台明细页直接显示 balance，且无账户数据时把正流水都当充值、负流水都当消费，包含 freeze/refund，统计错误。
- 数据库与 API 的单价仅为整数 `unitCredits`，TTS 每字符 1 积分等细粒度计费无法按真实低成本精确定价。
- 文本固定 `text_run`，没有保存输入、输出、缓存 Token；图片尺寸/质量系数为平台固定倍率，视频请求时长可能与上游归一化时长不一致。
- `vendorCostCny` 缺少来源、币种、单位、模型版本、地域、核验时间。不可将未知成本当 0 或实际账单。
- 任务积分锁序为 task → account，流水维护冻结/释放/消费。任务创建、内容生成、媒体任务、配音均依赖 `reserveTaskCredits`/`settleTaskCredits`/`releaseTaskCredits`，应复用这些并保持幂等。
- 会员折扣冻结原价、成功结算才减免。报价目前不说明实际会员应付，且退款与“释放冻结”混在 refund 类型。
- 管理员调整积分支持 requestId 幂等和余额不得低于冻结，但负向调整增加 totalConsume，需要区分人工扣减与生成消费。
- 流水全部一次性拉取，前台仅本地分页；后台缺少统一账户、资金批次、任务报价/实扣/成本、对账中心。
- 充值与支付已支持订单幂等、受验证的微信回调、原子入账、会员续费；卡密原子兑换。真实微信支付关闭，不能为了本轮开发擅自开启或模拟现金验收。
- 本地基线 b875e63，生产仍为 5df3bb0；前一轮真实隔离 API 270/270、FFmpeg 编码/解码通过。当前会话 GitHub 连接已要求新会话衔接，不能重试该连接服务或旧 credential-channel。

## 目标技术契约

1. 新建共享精确计费引擎，内部以整数微元/有理数计算，钱包仍使用整数积分；全次/全批求和后一次向上取整，不能按每字符先取整。目标毛利 40%，折扣和赠送应有毛利预览与保护选项。
2. 定价政策持久化：名义积分价值、目标毛利、USD 结算汇率、运营费用参数、促销保护、生效版本。成本规则支持人民币/美元、文本输入输出与缓存、整请求阶梯、图片按张/规格、视频按秒/音频/分辨率、TTS 按万字符、核验来源和日期。保留现有手工模式；只有来源明确的规则可以自动换算并发布。
3. 每次任务保存不可变报价快照、定价版本、原价/会员实付/积分上限、模型与单位。真实供应商 usage 被计量后按快照结算；不能在结算时读被管理员新修改的单价。新报价应明确冻结应付，不允许未知结果触发第二次提交或扣费。超出确认上限不得静默多扣。
4. 为成本与现金收入引入来源明确的入账批次/计量账本。支付本金及附赠额度、卡密/推广、手工调整、历史余额分类；历史资金成本未知，不能杜撰实收收入。如果使用钱包资金批次，应保持总额、冻结和每任务占用一致，FIFO 消费，部分成功只扣成功项，释放剩余冻结。
5. 供应商 usage 记录与实际现金账单区分；供应商调用已产生费用但交付失败时，平台退款仍记录该成本。报价预估、usage 推导、真实账单核对使用不同状态。
6. 管理后台增加“积分中心”：账户与可用/冻结、流水服务端分页/筛选/导出、资金来源、任务对账/异常、定价公式与毛利计算器、官方成本规则及同步预览/应用、套餐赠送和会员优惠毛利影响。沿用 sub2API 风格和现有管理权限、操作审计、冲突版本保护。
7. 用户端展示可用/冻结/总余额、生成前报价与实扣/解冻、会员优惠、用量和计费单位；明细可筛选搜索并服务端分页。金额不足提供差额和充值路径，已成功但刷新失败不能让用户重复提交。
8. 测试覆盖整数精度、微小 TTS、Token 缓存/阶梯、汇率、40% 与折扣/赠送、并发冻结/结算/退款、政策变更快照、支付/卡密幂等、人工调整、历史未知成本、分页/权限/CSV、前台与后台桌面/手机。真实隔离数据库测试复用前轮临时 Docker 方法，绝不使用生产库或真实客户素材。

## 最终实现契约

- `packages/shared/src/creditPricing.ts` 使用 BigInt 有理数；费用按整任务求和、最终积分向上取整。官方目录只包含已核验阿里北京原价，DeepSeek 必须人工确认冲突、币种与时段。
- `ModelPrice.billing` 为可选成本规则。空值沿用现有手工计价；管理员在“积分中心”先预览、再应用单条规则，不自动绑定未知模型。手工单价编辑不能静默覆盖已启用的自动成本规则。
- `CreditPricingPolicy` 持久化基础政策及版本。保护模式取已启用充值/会员套餐与尚有剩余积分的历史 `paid` 批次中最低实收积分价值，停售或调价不能隐藏已有低价积分。资金查询使用 `source/remainingCredits` 索引，耗尽批次退出保护；实收低于每积分一微元的异常批次阻止保护模式报价。自动规则以成本底价限制会员减免，实际减免保存在任务快照；手工价格保留会员权益。推广赠送、未知实收、交付失败产生的费用、封顶补贴不保证现金40%毛利。
- `GenerationTask.billingQuote/billingUsage/billingSettlement` 保存不可变价格、供应商计量和账务结果。新任务冻结应付，结算不读新价格；超确认上限封顶由平台承担，并标记异常。历史已有冻结保持原规则。
- 文本通过 AsyncLocalStorage 在解析输出前采集 usage，失败请求成本保留。计量绑定执行轮次 `attemptId`，前一轮生成成功但写库失败或租约被接管的响应不参与本轮用户交付扣费，其供应商成本仍保留。取消后迟到的计量更新成本证据，已核验账单不被usage覆盖。图片/视频/配音在无 provider usage 时按交付数量推导成本，明确标记 `output_quantity`，不冒充真实账单。
- `CreditFundingLot` 首次新操作时将旧余额补为 `legacy_unknown`，新核验在线收款保存实收，奖励为 `gift`，卡密和人工增加实收未知。用户外键级联清理，单调递增 `sequence` 保证同事务时间戳下的FIFO顺序。FIFO 在实际结算顺序分摊，累计微元差额法防止分摊舍入丢失；任务冻结所有权仍由 task ledger 管理，不宣称资金批次已逐任务冻结。
- 新后台接口沿用 `billing:manage` 与写审计，定价政策和成本规则版本冲突返回409。账户、任务、流水服务端分页，资金批次最近100条。前后台CSV都导出当前筛选页，保留原始 `page/pageSize`，不把第二页改回第一页。真实账单核验不修改用户消费；仅在现金来源与真实账单均核验后显示现金毛利率。
- 前台侧栏、资料和明细统一显示可用积分，明细另外标出总余额和冻结。日期筛选使用用户本地开始日00:00至结束日23:59:59.999，再转ISO提交。手机流水保持完整标签和表格横向滚动。自动TTS参考价标为每万字符，文本标为参考次并说明实际按Token。
- 注册手机号文案按用户最新要求改为“11位手机号”，注册说明、格式错误和验证码邮件中去掉资料收集措辞。SMTP 开通说明更新为 QQ 官方现行入口。
- 账户核对包括累计生成消费、冻结流水、资金余额和历史未归档积分；任务核对包含上限、实扣、释放、官方成本证据、实收分摊、路线不匹配和封顶补贴。并发/快照/FIFO/退款/权限等以真实隔离PostgreSQL验收为准。UI夹具、真实数据库集成、供应商真实付费样片、微信现金收款和QQ真实送达分别记录，不能互相替代。
