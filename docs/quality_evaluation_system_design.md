# 漫角评测体系设计

## 目标

评测系统不做“来一条数据就全量跑一遍”。核心目标是用可控成本回答三个问题：

1. 哪些项目、哪些阶段真的卡住了用户。
2. 哪些模型、提示词和流程能产出更高可用率。
3. 哪些优化动作能通过下一轮数据验证有效。

## 参考的成熟做法

成熟 LLM 评测平台通常拆成四层：

- Dataset：选择一批样本，不直接全量评测线上数据。
- Evaluator / Scorer：规则评分、人工反馈、LLM-as-a-Judge 都是不同评测器。
- Experiment Run：一次评测运行必须记录样本范围、评测器、模型、提示词版本和预算。
- Dashboard：对比分数、失败原因、用户反馈、成本和模型稳定性。

漫角当前按这个结构落地：规则评分默认随时可跑，LLM Judge 必须在后台显式选择项目、阶段、模型和调用上限。

## 数据选择策略

后台评测闭环页支持勾选项目样本和阶段：

- 优先选最新 1-3 个真实用户项目。
- 优先选低分、有用户反馈、有失败任务的项目。
- 阶段按瓶颈拆开跑：剧本、角色、分镜、图片、视频不要默认全选。
- 分镜和图片阶段默认只抽前 8 条镜头进入 LLM prompt，避免长项目消耗过高。

## 双通道评分

规则评分：

- 优点：便宜、稳定、可重复、适合全量趋势。
- 用途：前台质检刷新、后台漏斗、基础质量门槛。

LLM Judge：

- 优点：能理解剧情、角色一致性、分镜连贯性和用户反馈。
- 用途：抽样复核、对比 DeepSeek / 豆包 / ZML gpt-5.5 评测差异、发现规则评分覆盖不到的问题。

融合评分：

- hybrid 模式生成规则报告、各 LLM 报告和 ensemble 报告。
- ensemble 当前权重：规则 35%，LLM 平均 65%。
- 单模型失败不会中断整次运行，会记录跳过原因。

## 成本控制

每次运行必须设置：

- projectIds：最多 50 个。
- stages：至少 1 个阶段。
- evaluatorModels：最多 6 个。
- maxLlmCalls：最多 50 次，达到上限自动跳过。
- maxShotsPerPrompt：1-25，默认 8。

建议冷启动期：

- 日常只跑规则评分。
- 每天抽 3-5 个有反馈项目跑 hybrid。
- 每周用同一批样本对比 DeepSeek、豆包、ZML gpt-5.5，观察分数稳定性和是否贴近用户反馈。

## 后续迭代

1. 增加 EvaluationDataset 表，保存固定样本集。
2. 增加 EvaluationRun 表，保存每次实验运行配置和成本。
3. 增加 JudgePromptVersion，支持评测提示词 A/B。
4. 将用户反馈归因纳入评测模型准确率：用户标记不可用时，低分模型更可信。
5. 建立“人工复核小样本”，用来校准 LLM Judge 的严苛度。
