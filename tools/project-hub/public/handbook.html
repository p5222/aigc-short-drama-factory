01 · 先分清三个地方

GitHub 保存提交历史与代码；工作副本是开发与操作 Git 的目录；线上运行目录是服务实际运行的版本。三者通过明确的提交、拉取和发布衔接。

位置做什么不会自动发生什么
你的电脑 / Remote SSH 工作副本使用编辑器和 AI 修改代码，安装依赖、测试和调试。未提交、未推送的文件不会自动出现在另一台电脑。
GitHub保存功能分支，审查 PR，合并 main。推送功能分支不等于线上更新。
Project Hub 服务器工作副本集中管理多个仓库，拉取、审查、提交、推送和触发已配置发布。网页没有内置 AI 编程环境，也不会读取你电脑里的代码目录。
  1. 打开 Project Hub，使用平台独立账号登录。这里的账号不是 GitHub 账号。
  2. 如果侧栏已有目标仓库，直接选中并核对仓库地址。接入其他项目或确实需要同仓库另一工作副本时，才点击“添加”，填写易于区分的项目名称和 https://github.com/OWNER/REPO，再点“添加并克隆到服务器”。私有仓库须由管理员先给服务器配置访问权限；你在新电脑登录 GitHub 不会自动改变服务器凭据的权限。
  3. 等待克隆任务完成，查看当前分支、提交与任务日志。克隆失败时保留项目，可从日志判断原因后重试。
  4. 多个仓库会出现在侧边栏。同一仓库也可有多个独立副本，例如“开发工作区”和“发布工作区”。每次操作先确认项目名称与 GitHub 地址。

平台目前面向受信任的项目维护者，登录者可操作已注册的全部项目；不要把同一个账号分发给不应接触其他项目的人。仓库访问密钥和服务器发布目标由管理员在服务器配置。

02 · 换电脑的完整步骤

离开旧电脑之前

  1. 在编辑器保存文件，检查 git status。把这次需要继续的代码提交到功能分支，并推送 GitHub。
  2. 打开 GitHub 确认分支上能看到最新提交。记下仓库地址、分支名和最后提交信息。
  3. 环境变量、数据库、素材、未跟踪文件不会随 GitHub 自动迁移。本机开发配置按项目样例重新建立，需要的开发数据通过受控备份方式准备。生产密钥、数据库和素材留在服务器管理；不要把 .env、密钥或数据库备份加进代码仓库。

在新电脑继续本机开发

  1. 安装 Git、项目要求的 Node.js 和包管理器，以及你使用的编辑器 / AI 工具。先查看该项目的 README 和 package.json，使用项目声明的版本。
  2. 登录你自己的 GitHub 账号并配置 Git 认证。如果使用 GitHub CLI，运行 gh auth login，再运行 gh auth setup-git。
  3. 克隆仓库，然后切换到旧电脑已经推送的功能分支。下面以漫角私库为例，codex/my-feature 要替换成旧电脑已推送的真实分支名；其他项目换成对应仓库地址和目录名。
git clone https://github.com/p5222/aigc-short-drama-factory.git
cd aigc-short-drama-factory
git fetch origin
git switch --track origin/codex/my-feature
git status

如果该分支已经存在本地，使用 git switch codex/my-feature，再执行 git pull --ff-only。首次克隆的默认分支通常已经存在，不必重复创建。

  1. 按项目说明安装依赖，恢复必要的本机环境配置。对漫角项目，先阅读仓库中的部署与多设备操作文档，再启动本地服务。
  2. 用 git log -1 --oneline 核对最后提交，确认当前分支与原电脑一致后继续编辑、测试、提交、推送。以后在两台电脑之间轮换，都遵循“离开前推送、开始前拉取”。

只是用网页管理服务器项目

新电脑只需浏览器，打开 Project Hub 登录即可看到服务器保存的项目。无需把此工具复制到新电脑，也无需在新电脑安装 Git。网页的拉取与提交操作发生在服务器工作副本，不能替代你电脑上项目目录的 Git 操作，也不需要为网页发布给这台电脑添加 SSH 公钥。

使用公共或借用电脑后点击“退出登录”。平台账号由管理员管理；不要把 GitHub Token 或 SSH 私钥粘贴进网页登录框。

03 · 用本机 AI 工具开发

  1. 在你的编辑器或 AI 工具中打开本机克隆的项目。确认当前功能分支，描述具体需求与验收标准。
  2. 让 AI 修改代码后，审查差异并运行项目要求的测试、类型检查和构建。生成代码不等于通过验证。
  3. 在本机提交并推送功能分支，在 GitHub 创建 PR。合并后，回到 Project Hub 的发布工作副本，切换 main、拉取并发布。
git switch main
git pull --ff-only origin main
git switch -c codex/my-feature
# 在编辑器中修改并验证
git diff
git add path/to/reviewed-file
git commit -m "feat: 说明本次实际改动"
git push -u origin codex/my-feature

这里的命令由你在本机终端执行。网页只管理服务器工作副本，不会凭空提供 AI 自动编程能力；如果 AI 工具运行在本机，它改的也是本机文件。

04 · 使用 Remote SSH 在服务器开发

  1. 由管理员为当前电脑自己生成的 SSH 公钥开通专门的开发账号、SSH 功能和工作区目录。私钥留在当前电脑，只交付公钥；不要复制生产发布密钥或他人的私钥。平台登录、GitHub 权限与 SSH 开发权限彼此独立。
  2. Git-only 发布密钥不支持 Remote SSH、交互终端或端口转发，需另行授权。通过编辑器的 Remote SSH 连接，打开专门的开发工作副本。先运行 git remote -v 与 git status，核对仓库和分支。
  3. 如果希望网页看到这些文件改动，编辑器必须打开 Project Hub 当前项目对应的同一个工作副本。平台不会公开服务器目录；向管理员确认映射关系。管理员还需确认文件归属和访问权限。另一目录的修改不会在此项目中出现；也可以在远端开发目录提交、推送 GitHub，再到网页拉取。
  4. 切换功能分支，在编辑器或已配置的远端 AI 工具中修改并测试。AI 是否能访问远端文件，取决于你实际安装和配置的工具。
  5. 保存后回网页刷新状态，审查、勾选文件、提交与推送；也可以在远端终端完成相同 Git 流程。

不要直接在生产服务运行目录写代码，也不要在网页执行 Git 操作的同时用终端切分支、提交或拉取。多人开发应各有工作副本和功能分支，发布工作区保持干净。

05 · 网页中同步、提交和推送

  1. 选项目。侧边栏项目名称下会显示仓库。核对当前分支和提交。
  2. 刷新远端。点击“刷新远端分支”，更新 GitHub 分支信息；这一步本身不会合并代码。切换下拉框包含本地分支与远端分支，在下拉框选择目标后点“切换分支”，选择远端分支会建立对应本地跟踪分支。
  3. 拉取。“拉取当前分支”只允许快进更新。工作区有改动或历史分叉时，先在编辑器处理，不要覆盖文件。
  4. 建分支。从最新 main 开始，填写新功能分支名并点击“新建分支”，例如 codex/add-character-filter。main / master 不提供直接提交与推送。
  5. 审查差异。点击文件名预览文本改动，勾选本次需要提交的文件。受保护的配置与凭据文件不能预览或提交。一次最多提交 200 个文件。
  6. 提交。填写 1–1000 字符的清晰说明，再点“提交选中文件”。若已有暂存区或冲突，回到编辑器 / 终端确认处理。失败会保留提交说明和选择，先看原因再重试。
  7. 推送。点击“推送当前功能分支”。任务成功后，在 GitHub 确认提交；点击“打开 GitHub PR 页面”，在 GitHub 填写审查说明并创建 PR。漫角项目要查看 Verify project CI 的实际结果，通过审查与检查后再合并 main。

提交是保存到当前服务器工作副本；推送才是上传 GitHub。PR 链接只打开 GitHub 页面，平台不会自动创建、批准或合并 PR。

06 · 发布与核验：完成 Git 推送还不够

  1. 先在 GitHub 合并经过验证的功能分支。确认这次要发布的 main 提交。
  2. 选中配置了发布目标的服务器项目，点击“刷新远端分支”，等待完成；下拉选择 main 并点“切换分支”，再点“拉取当前分支”。每一步都要等任务完成。工作区必须干净，HEAD 必须与 GitHub main 一致。
  3. 点击“确认并发布 main”。检查弹层中的项目、仓库和完整提交，输入项目名称后点击“发布此提交”。平台绑定确认时的完整提交；提交发生变化时必须重新确认。
  4. 等待任务日志。若显示“服务器已接收代码，线上版本尚未核验”，只说明 Git 推送已被接收，构建或服务更新可能仍在进行。
  5. 点击“核验线上版本”。平台会核对服务器 main、deployed 与健康接口完整 40 位提交一致，且健康响应为 ok: true；同版本重试还需确认请求已被 hook 处理。漫角就绪地址为 https://manjiao.cloud/ready。全部条件满足时才显示“线上版本已核验”。这不是完整业务验收，仍应打开网站检查此次改动的实际流程。
页面状态含义与下一步
执行中查看日志，等待完成，不要重复发布。
服务器已接收 / 待线上核验查看构建与运行状态，稍后重新核验。不能据此宣称网站已更新。
线上版本已核验提交一致；继续做与本次改动相关的实际业务验收。
失败 / 已中断先读日志、刷新 GitHub 与工作区状态，核对是否部分完成后再决定安全操作。

若服务器已接收同一提交，但构建失败或线上仍未更新，请先处理日志中的实际原因，再点击“重试同一版本发布”。该按钮仅在持久发布记录为待核验、当前完整提交与上次一致时可用；弹层会再次确认项目与提交，输入项目名称后点击“重试发布此提交”。普通重复推送相同 main 不会重新触发发布；重试后仍需核验线上版本。

“尚未配置发布目标”的项目仍可正常拉取与推送，但不能直接发布。服务器管理员需在私有配置中按仓库设置可信的 remote、verifyUrl 和配套发布 hook；网页不能配置任意命令或地址。新项目还应具备自己的测试、备份和运行服务，不能因 clone 成功就视为可发布。数据库迁移、备份、素材存储和回滚方案要跟随项目自己的发布流程；工具不会把这些内容当作普通代码自动同步。

需要回滚时

  1. 记录问题提交与最后一次已核验版本，在新的 codex/revert-任务名 功能分支撤回问题代码；普通提交可使用 git revert，合并提交需由维护者确认主线，不能直接照抄命令。
  2. 运行验证，通过 PR/CI 将回退作为新的 main 提交合并。
  3. 回平台选择项目，刷新远端、切换并拉取 main，再确认发布与核验。平台没有一键回滚、强推主线或自动丢弃改动按钮。

代码回滚不会撤回数据库或客户素材的新写入。紧急恢复由管理员按项目运行手册、备份与数据库兼容性处理，不删除生产数据卷或把旧备份直接覆盖正在使用的数据。

07 · 研发团队如何迭代？

你可以使用同样的方式。人数少时不必增加复杂流程，但要让每次改动可检查、可接续。

  1. 确定一个可验证的需求：记录目标、影响页面和完成标准。
  2. 独立分支开发：每人使用自己的工作副本；一次分支聚焦一个需求或修复。
  3. 提交与自动检查：运行测试和构建，提交小而清晰的变更。
  4. PR 审查与合并：核对差异、测试结果和数据兼容性后合并 main。一个人也可以在 PR 中做一次独立自查。
  5. 发布、核验、观察：发布明确版本，检查网站流程和运行日志，再开始下一次迭代。

Project Hub 负责多项目的 Git 同步与发布入口。任务拆分、AI 编程、代码审查、权限细分和业务验收仍需要相应的工具与真实执行。

08 · 遇到问题时

新电脑看不到旧电脑最新代码

检查旧电脑是否保存、提交并推送成功，以及新电脑是否切到同一远端分支。未提交文件只能回旧电脑或备份中找回；网页无法恢复未上传的本机内容。

网页登录成功，但克隆私有仓库失败

查看任务日志。平台账号和 GitHub 凭据是两回事，管理员需要给服务器凭据授予该仓库访问权限。不要反复添加重复项目，原项目可重试克隆。

提交、切换或拉取按钮不可用

当前项目有运行任务时会暂时禁用。主线不能直接提交和推送；切分支、拉取与发布需要干净工作区。已有暂存内容或冲突时，先在编辑器处理，再刷新状态。

请求超时，能直接再点一次吗？

先刷新项目和任务记录。超时只表示浏览器没拿到结果，服务器可能仍在执行；重复提交可能造成重复项目或多次操作。确认日志和 Git 状态后再重试。

拉取失败，提示不能快进

本地与远端历史可能分叉。回到编辑器检查两边提交，通过受控合并、变基或 PR 处理，解决冲突并测试。不要用强推或重置来绕过未知差异。

已经推送 GitHub，线上页面仍是旧版本

功能分支推送、PR 合并和服务器发布是不同步骤。先确认 PR 已合并，再同步发布工作区的 main、发布并核验线上提交。若只显示“已接收”，继续查构建日志和健康状态。

服务重启后任务显示“已中断”

任务可能已经部分执行，必须重新读取工作区状态并检查 GitHub 或线上提交。审计记录会保留中断信息，不会把未知结果记成成功。

环境变量、数据库或素材怎么换电脑？

Git 管理代码，不承担所有业务数据迁移。按项目文档恢复环境配置与数据，使用单独的受控备份或对象存储。密钥不要提交 GitHub；生产数据不要直接复制到不受控的个人电脑。

平台账号忘记密码，或要给新电脑开 SSH

联系平台管理员调整服务器上的账号配置或登记新电脑的 SSH 公钥。网页没有假设存在“找回密码”邮件服务，也不会自动开放服务器 SSH 给所有来源。
